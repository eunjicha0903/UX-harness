## 3. 재실행

- 디자이너가 수정하면 S1부터 다시 실행한다. S1에서는 바뀐 자료만 새로 스냅샷한다.
- 재검증 기준은 ① 현재 Figma 화면, ② Notion 검토 사항 DB의 사용자 입력이다.
- '수정 완료' 체크 항목: S2~S4에서 해당 항목을 우선 재판정하고, 결과를 '재검증 결과'에 기록한다. 체크 자체는 바꾸지 않는다.
- '컨펌 완료' + '결정 메모': 해당 NEEDS_REVIEW를 해소로 처리한다. 결정 메모가 비어 있으면 해소로 인정하지 않는다. 컨펌 이후 근거 자료(Figma 노드·PRD)가 바뀌었으면 해소를 취소하고 다시 판정한다.
- 체크가 없는 미해소 항목도 매 실행마다 다시 판정한다 (전체 검증).
- 이전 실행 결과는 수정 이력으로 남기고, 항목별 이전 판정 → 현재 판정 변화를 기록한다.

## 6. 화면 판별 규칙 (공통 기본값, 프로젝트별로 story-service에서 재지정 가능)

1. 지정한 Figma 페이지의 최상위 프레임 중 이름이 `숫자.` 또는 `숫자_`로 시작하는 것을 화면으로 센다. 번호 순으로 정렬한다.
2. 화면 ID는 `플랫폼-번호` 형식으로 쓴다 (예: `APP-01`, `WEB-01`). 플랫폼은 프레임 크기로 구분한다 (375 폭 = APP, 1920 폭 = WEB, 프로젝트별 재지정 가능).
3. 프레임 이름은 Figma에 적힌 그대로 매칭한다. 오타는 고치지 않고 S3 용어 일관성 검사에서 따로 잡는다.
4. 번호가 같은 프레임은 같은 화면의 상태 변형으로 묶는다.
5. `수정 반영` 같은 변경 기록 섹션은 화면 목록에 넣지 않고, 해당 화면을 덮어쓰는 최신 기준(override)으로 연결한다.
6. `TAG`, 로고, `컴포넌트` 등 화면이 아닌 프레임은 제외한다.

이너베러: 사용자앱은 `01.회인가입/로그인`, 관리자웹은 `01.로그인`부터 시작한다 (concept 페이지만 사용).

## 7. 수정 피드백 입력 (사용자 확인 2026-10-25)

사용자가 수정 피드백(텍스트, 카톡·노션 메모 등)을 주면, 전체 검증을 실행하면서 피드백을 영향 분석의 기점으로 추가한다. Figma에 아직 반영되지 않은 "계획된 변경"이어도 된다.

1. S1: 피드백을 항목 `FB-<run-id>-<번호>`로 나눈다. 항목마다 대상(화면·컴포넌트·기능·데이터·정책), 변경 내용, 원문, Figma 반영 여부(반영됨/미반영, 정보용)를 기록한다. 피드백 원문은 `source_id: FB` (사용자 제공, FETCHED)로 등록한다. 대상을 특정할 수 없는 항목은 `INSUFFICIENT_INFO`로 기록한다.
2. S2·S3: 피드백대로 바꾸면 요구사항·필수 규칙·컴포넌트 상태와 충돌하는지 판정한다. 필수 규칙과 충돌하면 해당 조건 ID를 `rule_ref`로 단 `FAIL` 레코드를 만든다 (GR에 반영).
3. S4: 피드백 항목마다 영향 분석 7개 항목을 채우고, **고려해야 할 영역**(화면·컴포넌트·데이터·상태·권한·정책·플랫폼별)과 관련 화면별 수정 필요/수정 불필요/추가 확인 필요를 판정한다. 정책 값을 바꾸는 피드백은 story-service 갱신(H0 재승인) 필요 여부를 `NEEDS_REVIEW`로 남긴다.
4. report.md 맨 앞에 "피드백 영향 영역" 섹션을 둔다.
5. 피드백의 Figma 미반영 자체는 FAIL로 판정하지 않는다.

## 8. 실행 중 질문 금지

검증 실행(S1~S5) 중에는 사용자에게 묻지 않는다. 판단할 수 없는 것은 판정 규칙(harness-goal §5)에 따라 `NEEDS_REVIEW`·`INSUFFICIENT_INFO`로 기록하고 계속한다. 결과는 실행이 끝난 뒤 한 번에 보고하며, 상태가 "검토 필요"(미승인)이면 미해소 항목별 사유를 함께 보고한다.
