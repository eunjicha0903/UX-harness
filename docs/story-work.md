# story-work.md

> 이 문서는 내가 실제로 업무를 진행하는 순서와 각 단계에서 판단하고 확인하는 기준을 기록한다.
>
> - **무엇을 위한 일인지:** `story-service.md`를 기준으로 한다.
> - **어떻게 진행하는지:** 이 문서의 작업 흐름을 기준으로 한다.
> - **어떤 기준으로 검토하는지:** 기획 의도, 기능 명세, 사용자 흐름, 예외 상황, 변경 영향 범위를 확인한다.
> - 이 문서는 특정 프로젝트에 종속되지 않는 공통 업무 프로세스다.

## 1. 작업 문장

1. 나는 견적서, 기능 명세서, 기존 화면 및 관련 자료를 확인하고 프로젝트의 요구사항을 파악한다.
2. 나는 기획 단계에서 변경되거나 추가된 요구사항을 확인하고, 기존 기획 및 기능 명세와 달라진 부분을 정리한다.
3. 나는 변경사항이 사용자 흐름, 기능 동작, 데이터, 상태, 권한 및 다른 화면에 미치는 영향을 검토한다.
   - ⏸ **멈칫:** 변경사항의 목적과 근거가 명확한지, 기존 기능과 충돌하거나 누락되는 조건은 없는지 확인한다.
4. 나는 요구사항과 검토 결과를 반영해 화면 설계 문서를 구체화하고, 화면별 목적과 주요 동작을 정리한다.
5. 나는 화면 설계서를 토대로 1차 기획 와이어프레임을 제작한다.
6. 나는 1차 와이어프레임을 화면별로 검토하고, 요구사항 누락·사용자 흐름·상태별 동작·예외 상황 및 화면 간 연결 관계를 확인한다.
   - ⏸ **멈칫:** 화면 자체는 완성되어 보여도 실제 기능이 성립하지 않거나 다른 화면과 연결되지 않는 부분이 없는지 확인한다.
7. 나는 검토 결과를 바탕으로 수정사항을 정리하고, 영향받는 화면과 기능을 확인한 뒤 와이어프레임 및 화면 설계서를 수정한다.
8. 나는 수정된 기획안을 다시 검토하고, 주요 수정사항이 반영되었는지 확인한 후 내부 관계자와 협의해 기획을 확정한다.
9. 나는 uibowl에서 경쟁사 레퍼런스를 수집하고, 서비스 목적과 클라이언트 니즈에 맞는 참고 요소를 분석한다.
   - ⏸ **멈칫:** 레퍼런스의 외형만 모방하지 않고, 우리 서비스의 목적과 사용자 요구를 충족하는 요소인지 판단한다.
10. 나는 확정된 화면 설계와 레퍼런스를 바탕으로 Figma에서 UI 키스크린 2~3개를 375×812 크기로 제작한다.
11. 나는 내부 관계자들과 협의해 컨셉 시안을 확정한다.
12. 나는 컨펌된 시안을 기반으로 디자인 토큰과 컴포넌트를 만들고 전체 화면 디자인을 진행한다.
13. 나는 완성된 디자인에서 디자인 가이드 위반 여부와 컴포넌트의 일관성을 검토한다.

## 3. 기획 변경사항 검토 기준

기획 변경사항이 발생하면 변경된 항목만 수정하지 않고, 기존 요구사항과 연결 관계를 함께 확인한다.

- **변경 내용:** 무엇이 추가·삭제·변경되었는가?
- **변경 근거:** 사용자 요구, 클라이언트 요청, 정책 변경, 기존 기획 오류 중 어떤 이유인가?
- **기능 영향:** 기존 기능의 동작이나 조건이 달라지는가?
- **화면 영향:** 다른 화면, 진입 경로, 뒤로 가기, 이동 경로에 영향이 있는가?
- **상태 영향:** 로딩, 빈 화면, 성공, 실패, 중복 처리 등 상태별 동작이 달라지는가?
- **데이터 영향:** 입력값, 저장값, 표시 정보, 데이터 전달 및 갱신 방식이 달라지는가?
- **권한·정책 영향:** 사용자 유형, 관리자 권한, 노출 조건 또는 업무 정책에 영향이 있는가?
- **연관 기능 영향:** 다른 기능이나 공유 컴포넌트의 동작이 달라지는가?
- **확인 필요 사항:** 근거 자료가 부족하거나 담당자 확인이 필요한 항목은 무엇인가?

검토 결과는 각 항목을 다음 중 하나로 구분한다.

- `수정 필요`: 변경 또는 오류가 확인되어 수정해야 한다.
- `수정 불필요`: 관련 범위를 확인했으며 변경할 필요가 없다.
- `추가 확인 필요`: 자료가 부족하거나 관계자 확인 없이는 판단할 수 없다.

## 4. 1차 와이어프레임 검토 기준

1차 와이어프레임은 시각적인 완성도보다 **기능과 사용자 흐름이 논리적으로 성립하는지**를 우선 검토한다.

1. **요구사항 충족:** 기능 명세서와 화면 설계서의 필수 요구사항이 반영되었는가?
2. **사용자 흐름:** 사용자가 진입부터 주요 작업 완료까지 진행할 수 있는가?
3. **기능 동작:** 버튼, 입력, 선택, 저장, 취소, 이동 등의 동작이 명확한가?
4. **상태별 처리:** 로딩, 빈 데이터, 오류, 성공, 비활성화 등 필요한 상태가 정의되었는가?
5. **예외 상황:** 잘못된 입력, 중복 요청, 데이터 없음, 권한 부족 등의 상황을 처리할 수 있는가?
6. **화면 간 연결:** 이전·다음 화면과의 이동, 데이터 전달 및 상태 유지가 일관적인가?
7. **정책 및 권한:** 사용자 유형별로 가능한 행동과 노출 정보가 적절한가?
8. **운영·관리 기능:** 관리자 화면이 있다면 사용자 화면과 데이터 및 상태가 일치하는가?
9. **수정 영향 범위:** 한 화면의 수정이 다른 화면, 공유 컴포넌트 또는 관련 기능에 영향을 주는가?
10. **미확정 사항:** 기획 의도나 정책을 추측해야만 설계할 수 있는 항목이 남아 있는가?

## 5. 수정 및 재검토 원칙

- 수정사항마다 관련 요구사항과 근거를 연결한다.
- 한 화면의 변경이 다른 화면이나 기능에 미치는 영향을 확인한다.
- 변경된 부분뿐 아니라 기존 동작이 유지되어야 하는 부분도 확인한다.
- 근거가 부족한 정책이나 기능을 임의로 확정하지 않는다.
- 수정 후에는 해당 항목의 반영 여부와 연관 화면의 영향 여부를 재검토한다.
- 검토 결과와 미해결 사항을 구분하고, 확인이 필요한 항목은 담당자에게 전달한다.
- 관계자 컨펌이 필요한 단계와 실제 컨펌 완료 여부를 구분한다.

## 6. AI 하네스 적용 시 원칙

이 문서는 실제 업무 흐름을 정의하며, AI가 모든 단계를 자동으로 승인하거나 대신 결정하도록 하는 문서가 아니다.

- AI는 관련 자료를 바탕으로 누락, 불일치, 영향 범위 및 확인 필요 사항을 찾아낸다.
- AI는 근거가 확인되는 사항과 추정 사항을 구분한다.
- AI는 수정이 필요한 항목과 수정할 필요가 없는 항목을 구분해 제시한다.
- AI는 자료 부족으로 판단할 수 없는 항목을 임의로 통과시키지 않는다.
- AI가 제안한 수정사항은 사용자가 검토하고 확정한다.
- 관계자 컨펌과 기획 확정은 실제 승인 여부를 확인한 뒤 완료 처리한다.
